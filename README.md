# Бюджетный харнесс для openJiuwen

Харнесс решает набор задач четырёх типов (math, search, data_analysis, coding) под одним общим бюджетом токенов. Главная
мысль: не отдавать модели то, что можно решить без неё.

1. Сначала идёт проход детерминированных решателей (`det_solver.py`). Если формулировка задачи совпала с известным
   шаблоном, ответ находится разбором условия и вычислением, без обращения к модели. Если по условию и данным задачу
   заведомо нельзя решить, файл ответа не создаётся.
2. Остальные задачи планировщик выстраивает по выгодности (`reward · p(успех) / ожидаемые токены`) и отдаёт `ReActAgent`
   из openJiuwen с единственным инструментом `bash`. По умолчанию работает дешёвая модель без рассуждений. Более сильная
   подключается, только если не прошёл локальный тест.
3. Расход считает собственный счётчик: прокси не сообщает остаток бюджета.

Что получилось:

* 8 примеров организаторов решаются верно за 0 токенов. 40 синтетических задач (32 выполнимые и 8 невыполнимых) тоже
  закрываются без модели.
* Если выключить детерминированный проход, те же 8 примеров проходят через движок openJiuwen на 20 баллов из 20 и
  стоят 3608 токенов (4562 без остановки по готовому ответу).
* Образ весит 1,36 ГБ при лимите 4 ГБ. Холодная сборка заняла 192 с при лимите 1000 с.
* Шаблоны проверены на настоящих базах знаний и таблицах из примеров, но формулировок скрытых задач мы не знаем.
  Незнакомая формулировка уйдёт к модели: это стоит токенов, а баллов обычно не стоит. Подробности в конце, в разделе
  «Что проверено, а что нет».

## Сборка и запуск

```bash
docker build -t hack:latest .

docker run --rm --name run-$TEAM \
  --network hack-net \
  -e LLM_BASE_URL -e LLM_API_KEY \
  -v "$TASKS:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 8 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python \
  hack:latest /app/run_agent.py --tasks-dir /data/tasks
```

Образ собирается на `python:3.12.16-slim-bookworm`. 159 зависимостей закреплены в `requirements.txt` (файл получен из
`requirements.in` командой `uv pip compile --python-version 3.12 --python-platform x86_64-unknown-linux-gnu`) и ставятся
только из готовых колёс (`pip --only-binary=:all:`), без компиляции. Всё скачивается при сборке, при запуске ничего не
загружается: LLM-путь openJiuwen мы прогнали в контейнере с флагами организаторов во внутренней сети Docker, где был
доступен только мок прокси. Ключей в репозитории и в образе нет. pip работает с 10 повторами и таймаутом сокета 100 с
(по умолчанию 5 и 15 с), чтобы единичный сбой сети не сорвал сборку с жёстким лимитом 1000 с.

Холодная сборка (`docker build --no-cache`, канал около 2,7 МБ/с) заняла 192 с, скачивается около 161 МБ колёс. Из 159
пакетов в нашем пути загружаются 85. Остальные 74 (около 69 МБ: `transformers`, `matplotlib`, `babel`, `pyoxigraph` и
другие) нужны openJiuwen для других подсистем. Мы их не вырезали: скачивание сократилось бы на треть, но сборка и так
укладывается в лимит с пятикратным запасом, а потерять нужный модуль в редко используемом пути не хочется.

`tools/smoke_image.sh` собирает образ и проверяет его в тех же ограничениях, что у организаторов (`--read-only`,
`--cap-drop ALL`, без сети): время сборки, размер против лимита 4 ГБ, офлайн-прогон на примерах, права на запись в
каталог задач и, если заданы `LLM_API_KEY` и `LLM_BASE_URL`, две задачи через настоящий LLM-движок внутри контейнера.
Нужен доступ к Docker.

Без Docker нужен Python 3.11–3.13 и `pip install -r requirements.txt`:
`LLM_BASE_URL=... LLM_API_KEY=... python run_agent.py --tasks-dir <каталог> --out <файл>`.
Проверить конвейер без сети и без токенов можно флагом `--fake-llm` (цикл на stdlib) или локальным моком прокси:
`python tools/mock_llm_server.py` печатает порт, после чего запускаем харнесс с
`LLM_BASE_URL=http://127.0.0.1:<порт>/v1 LLM_API_KEY=mock`. Мок подходит и для движка openJiuwen.

### Переменные окружения и параметры

| Переменная / флаг | По умолчанию | Смысл |
|---|---|---|
| `LLM_BASE_URL`, `LLM_API_KEY` | нужны для LLM-пути | адрес и ключ прокси (OpenAI-совместимый `/chat/completions`), нигде не печатаются. Без них работают только детерминированные решатели, в stderr будет предупреждение |
| `TASKS` / `--tasks-dir` | `/data/tasks`, если такой каталог есть | каталог с задачами |
| `OUT` / `--out` | `/tmp/solutions.json` | файл решений или каталог (тогда внутри `solutions.json`), см. «Выходные файлы» |
| `BUDGET` / `--budget` | 100000 | общий бюджет в выходных токенах (10 входных = 1 выходной), псевдоним `TOKEN_BUDGET`. Организаторы передают его в `BUDGET` |
| `PER_TASK_CAP` / `--per-task-cap` | 12000 | жёсткий потолок расхода на одну задачу |
| `MAX_PARALLEL` / `--parallel` | 3 | число потоков (у ключа для разработки лимит 3 параллельных запроса) |
| `TIME_LIMIT_S` / `--time-limit` | 3300 | после этого новые задачи не стартуют (жёсткий лимит запуска 1 час) |
| `REPAIR_TOTAL_S` | 600 | общий потолок времени мутационной починки coding на все задачи (на одну не более 30 с). Проход решателей последовательный и делит лимит запуска с этапом LLM. Реальные 29 задач тратят около 13 с |
| `TEST_MEM_MB` | 1024 | лимит памяти (`RLIMIT_AS`) дочернего процесса, в котором запускаются тесты `mylib.py` |
| `ENGINE` / `--engine` | `auto` | `openjiuwen`: только ReActAgent, без запасного движка (если openJiuwen не импортируется, запуск останавливается, сбой внутри оставляет задачу без ответа). `loop`: цикл на stdlib, без openJiuwen. `auto`: openJiuwen, при сбое запасной цикл |
| `TIERS` | `qwen3.6-35b-a3b-noreason,qwen3.8-27b-noreason` | порядок моделей для эскалации |
| `LOG_DIR` / `--log-dir` | `$TMPDIR/ojw_logs` | `calls.jsonl` и траектории `traj/<task>.json` |
| `NO_PRECHECK` / `--no-precheck` | выкл. | отключить проверки выполнимости без LLM (для замеров самого решателя) |
| `AUTO_STOP=0` / `--no-auto-stop` | выкл. | отключить остановку по готовому `answer.txt` (нужно только для сравнения расхода) |
| `DETERMINISTIC=0` / `--no-deterministic` | выкл. | отключить проход детерминированных решателей: все задачи уйдут к LLM (для замеров и отладки) |
| `--resume` | выкл. | пропустить задачи, уже записанные в файл `OUT` |

Итоговая команда запуска может отличаться от регламентной, поэтому разбор аргументов терпимый. Каталог задач принимается
как `--tasks-dir`, `--tasks` или `--tasks_dir`, файл решений как `--out`, `--output`, `--solutions`, `-o` и другие
синонимы. Два позиционных аргумента читаются как каталог задач и файл решений. Неизвестный аргумент игнорируется с
предупреждением в stderr и не роняет запуск.

## Как это устроено

```
run_agent.py   загрузка задач → план → пул потоков → запись результата после каждой задачи
 tasks.py      чтение task.json (поля expected/check не читаются), признаки задач
 prechecks.py  проверки выполнимости без LLM (0 токенов)
 planner.py    оценка p(успех) и стоимости, порядок по reward·p/стоимость
 budget.py     общий счётчик токенов, резервы, потолки
 llm.py        клиент прокси (stdlib), только 4 разрешённые модели, повторы, учёт usage
 solver.py     BaseSolver: политика (IMPOSSIBLE, эскалация, потолки), локальная проверка тестов;
               ToolLoopSolver: запасной движок на stdlib
 det_solver.py детерминированные решатели шаблонных задач (0 токенов), проход до планировщика
 repair.py     мутационная починка mylib.py с проверкой тестами (этап coding в det_solver.py, 0 токенов)
 ojw_solver.py OjwSolver: движок на openJiuwen ReActAgent + LedgerModel (учёт токенов, повторы)
 results.py    запись answer.txt и файла OUT после каждой задачи (атомарно)
 tools/        probe_usage.py (замер формата usage), mock_llm_server.py (мок прокси для офлайн-тестов),
               gen_tasks.py (генератор синтетических задач в форматах примеров), grade_run.py (оценка прогона),
               check_det.py (детерминированные решатели без токенов), check_edge_cases.py (71 граничный случай),
               check_search_chains.py и check_data_filters.py (цепочки в kb и фильтры sales.csv на настоящих данных),
               check_math_chains.py (случайные истории о складе с независимой симуляцией),
               check_startup.py (запуск при неудобных OUT/LOG_DIR и без ключа),
               check_bug_zoo.py (92 варианта бага в 20 функциях), check_repair.py (мутационная починка),
               run_all_checks.sh (все проверки одной командой), smoke_image.sh (сборка и проверка образа)
```

Агент работает в `workspace/` задачи: инструкции говорят «current directory», и файлы лежат там. Если `workspace/` нет
(например, у math), создаётся пустой временный каталог, чтобы агент не видел `task.json`. Дочерний процесс `bash`
получает минимальное окружение и не видит `LLM_API_KEY` и `LLM_BASE_URL`.

**Остановка по готовому ответу** (`solver.answer_ready`, работает в обоих движках). Сначала каждая задача заканчивалась
отдельным вызовом, в котором модель просто писала `DONE`, а вся история шла на вход ещё раз. В data_analysis к этому
добавлялся проверочный `cat answer.txt`. Теперь попытка завершается сразу после команды, если одновременно выполнены три
условия: в каталоге есть непустой `answer.txt` (устаревший удаляется в начале каждой попытки), последняя команда не
завершилась ошибкой (`[exit N]`) и не истекла по времени, а локальные тесты (если они есть) проходят. Если тест падает,
диалог продолжается как раньше, поэтому на корректность это не влияет. В openJiuwen `LedgerModel.invoke` в такой
ситуации возвращает синтетическое сообщение `DONE` и ничего не списывает. Проверка тестов вынесена в отдельный поток,
чтобы не блокировать общий цикл событий.

## Детерминированные решатели (без LLM)

Организаторы разрешили решать задачи без модели («можно решить все, если получится»). `det_solver.py` запускается до
планировщика и стоит 0 токенов. Правило такое: решатель отвечает, только если сам вопрос совпал с известным шаблоном
слово в слово (якорные регулярные выражения) и данные согласованы. Иначе он возвращает `nomatch`, и задача идёт к LLM.
Отказ стоит токенов, а неверный разбор или ложное «невыполнима» стоили бы баллов, поэтому лучше отказаться. Исходов три:
`answer` (пишем `answer.txt`), `unsolvable` (шаблон совпал, но данных заведомо не хватает, файл не создаётся) и
`nomatch` (к LLM).

Вокруг вопроса допускается разное оформление. Хвост инструкции («Work only inside … write ONLY the final answer to the
file answer.txt …») может по-другому говорить о месте файла, например «next to task.json», а повелительные подсказки без
чисел («Compute it …», «Use bash …») могут быть переписаны. Другой файл, путь или число внутри подсказки означают
`nomatch`.

**math.** Склад: старт и последовательность операций над одним запасом в любом порядке и любой длины. Распознаются:
«ships X boxes [per day for D days]», «receives X boxes [per day for D days]», «receives R deliveries of Q boxes each»,
деление на K с округлением вниз или вверх, удвоение, утроение и учетверение (с концовкой «by merging with … sister
warehouse(s)», но только если она согласуется с множителем). Перед операцией допустимо «Then», числа могут быть цифрами
или словами. К LLM уходят неизвестные предложения, несогласованная концовка, десятичные числа, «rounded to the nearest»,
скорость без срока («per day» без «for D days») и другие глаголы. Невыполнимой считается задача, где вместо числа стоит
неопределённое количество («some», «several», «an unknown number of») или пустой слот в известном предложении («It ships
boxes per day for 3 days», «split equally into warehouses»): в решаемом тексте такого быть не может.

**data_analysis.** `sales.csv`, две метрики: сумма `units` и выручка `units * price` (она названа в самом вопросе). К ним
добавляются необязательные фильтры в фиксированном порядке: товар, регион, месяцы («in months A through B inclusive» или
«in month M»). Формулировки из примеров попадают в эту грамматику как частные случаи. Заголовок и число строк должны
совпасть с инструкцией, столбцы быть числовыми. Невыполнимой считается задача, которой нужен столбец, отсутствующий в
файле, или понятие, которого нет среди столбцов (`discount`, `tax`, `profit` и подобные). Слово «cost» к таким не
относится: оно может означать `units * price`.

**search.** `kb/` читается как граф: человек → наставник → человек и человек → работодатель → компания. Цели: год
рождения, город штаб-квартиры, год основания, имя наставника, название работодателя. У каждой цели несколько
перефразировок («What is the birth year of …», «Where is the headquarters of …», «Which company employs …»). Перед целью
может стоять цепочка наставников любой глубины до 12, записанная как «X's mentor's mentor», «the mentor of the mentor of
X» или вперемешку. Работодатель задаётся как «X's employer», «the employer of X» или «the company where X works».
Заголовки записей должны быть вида `# Имя`. Неоднозначное имя, запись в незнакомом формате и упоминание в свободном тексте
уходят к LLM. Невыполнимой считается задача, где человека или компании нет в базе, либо запись есть, но нужного поля в
ней нет.

**coding.** `mylib.py` и `test_mylib.py`, текст инструкции точно как в примерах.
1. Есть библиотека канонических реализаций: `reverse_words`, `total`, `maximum`, `minimum`, `average`, `first_n`,
   `last_n`, `count_even`, `count_odd`, `product`. Функции подменяются по одной, пока число падающих тестов уменьшается.
2. Для остальных функций работает мутационная починка (`repair.py`). Она перебирает одиночные правки AST в копии рабочего
   каталога: оператор сравнения или арифметики, `and`/`or`, подмена `sorted`/`reversed`, `min`/`max`, `upper`/`lower` и
   т. п., константы ±1, границы срезов, индексы и аргументы `range`, лишняя строка, не та переменная, обёртка выражения
   в `reversed()`/`set()`/`abs()`, вызов метода `.lower()`/`.split()`/`.capitalize()`, `=` вместо `+=`, константа вместо
   `len(x)` или `x[0]`, граница среза не с той стороны, `range(e)` без старта, метод без скобок. Сначала перебираются
   только функции, на которые указывают падающие тесты. Правка принимается, если прогресс по тестам строго растёт (меньше
   упавших тестов или первое падение уходит ниже по тесту).
3. `DONE` пишется, только если прошли все тесты. Иначе остаётся исходный файл (или улучшенный шагом 1), и задачу берёт
   LLM.
4. Невыполнимой считается задача, где тесты не могут пройти: они противоречат друг другу (в разных методах, а в одном
   методе только если функция доказанно чистая) или заведомо падают (`assertEqual(1, 2)`, `assertTrue(False)`,
   `self.fail()`).

Чистота функции определяется по самому `mylib.py`: нет `global`, ссылок на переменные модуля, `random`/`time`,
изменяемых значений по умолчанию и вызовов нечистых функций. Функция со счётчиком вправе честно возвращать разное, поэтому
её вызовы противоречием не считаются.

## Движок openJiuwen

Задачу решает `ReActAgent` (`ojw_solver.py`): `agent.invoke({"query": инструкция})` с одним инструментом `bash`
(`LocalFunction`), нашим системным промптом (`configure_prompt_template`) и потолком шагов (`max_iterations`, одна
итерация равна одному вызову модели). Политику (IMPOSSIBLE, эскалация, потолки) он делит с запасным движком через
`BaseSolver`.

**Почему `ReActAgent`, а не `create_deep_agent`.** Мы сравнили `prompt_tokens` первого вызова одной и той же задачи на
реальном прокси. Запросы перехватывал локальный мок, затем они переигрывались с `max_tokens=1`; файлы лежат в
`trajectories/agent-first-request-payloads/`.

| Вариант | `prompt_tokens` |
|---|---|
| наш цикл на stdlib (системный промпт и `bash`) | 452 |
| `ReActAgent` с пустым системным промптом | 362 |
| **`ReActAgent` с нашим системным промптом (выбран)** | **452**, ровно как цикл: фреймворк ничего не добавляет |
| `DeepAgent` по умолчанию | 568 |
| `DeepAgent` без рейлов безопасности и аномалий | 434 |

`DeepAgent` дороже уже по умолчанию, заранее шлёт скрытый запрос с картинкой и держит повторы внутри рейла.
`ReActAgent` отправляет ровно то, что ему задали, и ведёт себя предсказуемо.

**Неочевидные детали openJiuwen 0.1.19, на которые опирается код:**
* **Повторов нет.** `ModelClientConfig.max_retries` в SDK не передаётся, повторы при сбоях есть только в рейле
  `DeepAgent`. `LedgerModel` сам повторяет 429, 5xx и таймауты (до 5 попыток, учитывает `Retry-After`). Запрос, который
  мог дойти до модели (таймаут, обрыв), списывается пессимистичной оценкой входа.
* **Ошибки.** Они приходят как `FrameworkError`, настоящая причина лежит в `__cause__` (исключения openai SDK). Для 401 и
  403 текст ответа выбрасывается: прокси возвращает в нём маску ключа.
* **`temperature` и `max_tokens` по умолчанию не заданы.** `LedgerModel` ставит их на каждый вызов, `max_tokens`
  ограничен остатком бюджета задачи.
* **Учёт токенов.** `LedgerModel.invoke` читает `usage_metadata` ответа (`input_tokens`, `output_tokens`) и списывает в
  `Ledger`. Потоковый `stream` запрещён, чтобы не обойти счётчик.
* **Логи.** По умолчанию библиотека пишет файлы в `./logs/` относительно текущего каталога, а при `--read-only` и
  `workdir /app` агент просто не стартует (`FrameworkError 183001`). До первого импорта openJiuwen `ojw_solver.py`
  меняет `DEFAULT_INNER_LOG_CONFIG`: только консоль и уровень `CRITICAL`. На уровне `ERROR` библиотека печатает промпты
  целиком, маску ключа и каждый наш осознанный повтор.
* **Скрытая проба.** `create_deep_agent` с `enable_read_image_multimodal=None` при старте отправляет отдельный запрос с
  картинкой (`max_tokens=64`).
* **Один цикл событий.** Все задачи идут на одном asyncio-цикле в фоновом потоке: общий HTTP-клиент библиотеки должен
  жить на одном цикле, а пул потоков в `run_agent.py` синхронный. Идентификаторы агента уникальны на каждую попытку
  (реестры инструментов и сессий общие на процесс). Блокирующий `bash` запускается через `asyncio.to_thread`.
* **Запасной переход.** Любое исключение самого фреймворка (не ошибка модели или авторизации) повторяет попытку запасным
  циклом, в консоль один раз печатается `WARNING`.

Результат на 8 примерах (`trajectories/run5-samples-openjiuwen`): 20/20, 4562 токена против 4571 у цикла на stdlib,
шаги совпали по каждой задаче.

## Учёт токенов

Стоимость вызова: `completion_tokens + prompt_tokens / 10` (в «выходных токенах»). Факты о прокси мы измерили
`tools/probe_usage.py`, сырые ответы лежат в `trajectories/proxy-usage-probe.json`.

* `usage.completion_tokens` уже включает токены рассуждений. У `qwen3.8-27b` это 34 токена при `reasoning_tokens=29`, у
  `qwen3.6-35b-a3b` 227 токенов при ответе в 4 символа и рассуждении в 629 символов (поля `reasoning_tokens` там нет
  вовсе). Поэтому `reasoning_tokens` к стоимости не прибавляются, иначе получился бы двойной счёт.
* Варианты `-noreason` не рассуждают: на тот же вопрос 3 токена против 34 и 227.
* В стриминге `usage` приходит последним чанком при `stream_options.include_usage`.
* Прокси не сообщает остаток бюджета (организаторы подтвердили это на установочной встрече), поэтому счётчик свой
  (`budget.py`). Адреса баланса и аккаунта харнесс не запрашивает: он обращается только к `/chat/completions`.
* У ключа для разработки лимит 120 запросов (окно не сообщается) и не более 3 параллельных (заголовки `X-Ratelimit-*`).
* Если запрос потерян по сети и мог дойти до модели, на счётчик ставится пессимистичная оценка входа (3 символа на
  токен). Если `usage` не вернулся, пессимистично оцениваются и вход, и выход.
* Резервирование: перед стартом задача резервирует ожидаемую стоимость. Если свободного бюджета не хватает только из-за
  резервов задач в работе, воркер ждёт, а не отказывается от задачи. Под резерв не отдаётся 10% бюджета.

## Оценка расхода и выбор задач

сейчас равна средней по реальным замерам с остановкой по `answer.txt` (32 синтетические выполнимые задачи в форматах
примеров, run8). Это грубая оценка, а не модель.

## Поиск невыполнимых задач

Три слоя, от самого дешёвого. Примеров невыполнимых задач организаторы не дали, поэтому слои 1 и 2 написаны под формат
примеров и консервативны: лучше пропустить проверку, чем отбросить решаемую задачу. На невыполнимые задачи другой формы
они не сработают.

1. **Планировщик, 0 токенов.** Каждый флаг умножает `p` на 0.1, и ниже порога 0.15 задача пропускается.
   * Инструкция упоминает файл или каталог, которого нет в `workspace/` (`missing:...`). Имена `answer.txt`, `task.json`
     и `workspace/` в тексте не считаются: хвост инструкции может говорить «next to task.json».
   * `search`: имён из вопроса нет в `kb/` (`entity-not-in-kb`) или у человека указан работодатель без файла компании
     (`employer-not-in-kb`). Флаг ставится, только если отсутствуют все названные сущности.
   * `coding`: в тестах одна и та же чистая функция модуля с литеральными аргументами проверяется `assertEqual` с двумя
     разными литералами в разных тестовых методах (`contradictory-tests`). Вызовы без аргументов и методы объектов
     (`stack.pop()`, счётчики) намеренно не рассматриваются: они могут честно возвращать разное.
2. **Системный промпт.** Модели разрешено ответить `IMPOSSIBLE`, тогда ответ не пишется и эскалации нет.
3. **Потолки.** Шаги: math и data_analysis 5, search 7, coding 9 (выполнимые примеры укладывались в 3, 3, 4–5 и 7).
   Есть и потолок токенов на задачу. На более сильную модель решатель переходит только если упал локальный тест, но не
   когда кончились шаги: модель посильнее не найдёт данных, которых нет (проверено, см. run2).

Известные пробелы. Модель сама почти не сдаётся и выдумывает ответ, если вопрос про несуществующий столбец CSV
(`data_analysis_9003`, около 1 тыс. токенов). А на противоречивых тестах, которые не поймал слой 1, она подгоняет код под
тесты (в run2 и run3 глобальным счётчиком вызовов), так что «тесты прошли» не доказывает, что задача решена.

## Выходные файлы и принятые допущения

* `answer.txt` пишется рядом с `task.json` (так ответили организаторы) и дублируется в `workspace/`, сразу после
  решения. Агент работает в `workspace/` и по инструкции пишет файл туда, а харнесс затем записывает тот же нормализованный
  ответ в каталог задачи. Если модель на LLM-пути запишет `../answer.txt` (рядом с `task.json`), ответ тоже будет найден,
  и для остановки по `answer.txt`, и после попытки.
* Файл `OUT` — JSON `{task_id: ответ}`. Он пишется атомарно (временный файл и переименование) после каждой задачи, рядом
  лежит `*.report.json` с расходом и причиной по каждой задаче.
* Для невыполнимых задач (`IMPOSSIBLE`, пропущенных, без ответа) файл не создаётся, этого требуют организаторы. Если
  модель успела написать `answer.txt` и затем сдалась, файл удаляется (`ResultStore.clear`).
* Ответ нормализуется: `680.0` → `680` (`solver.normalize_answer`). Модель часто суммирует через `float()` и пишет
  `680.0`, а проверка `exact_int` из примеров отвергла бы верное значение. Остальные ответы только обрезаются по краям.
* Регламент называет `OUT` «выходным файлом», но запускает `mkdir -p "$OUT"`, поэтому поддержаны оба варианта. В команде
  запуска из регламента в контейнер передаются только `LLM_BASE_URL` и `LLM_API_KEY`. Без явного `-e OUT` файл решений
  окажется в `/tmp` контейнера, и надёжный результат это `answer.txt` в каталогах задач.
* Побочные файлы не могут остановить запуск. `-e OUT` передаёт только значение, то есть путь хоста, а в контейнере с
  `--read-only` такого каталога нет и создать его нельзя (`Errno 30 Read-only file system`). Раньше в этом случае
  `resolve_out` падал до первой задачи, и не сохранялся ни один ответ: в контейнере с флагами организаторов получалось
  0 из 8, теперь 8 из 8. Сейчас любая неудача с `OUT`, каталогом логов или отсутствием `LLM_BASE_URL` и `LLM_API_KEY`
  только печатает предупреждение. Копия решений и логи уходят в `/tmp`, а без ключа работают детерминированные решатели
  (0 токенов). Если не заданы ни `--tasks-dir`, ни `TASKS`, каталог задач берётся из `/data/tasks` (это точка монтирования
  из команды запуска). Всё это проверяет `tools/check_startup.py`: 8 сценариев, на прежнем коде 5 из них дают 0 ответов.
* С `--cap-drop ALL` процесс от root не может обходить права доступа. Мы проверили это на собранном образе: если каталоги
  задач принадлежат другому пользователю и имеют обычные права (755/644), запись `answer.txt` и правка `mylib.py` дают
  `PermissionError`, и ни один ответ не сохраняется. При `chmod -R a+rwX` на каталог задач всё работает. Изнутри
  контейнера это не обойти, обеспечить запись должна среда запуска. Достаточно любой из двух строк, обе работают при
  любом владельце файлов: `chmod -R a+rwX "$TASKS"` перед `docker run` либо `--user "$(id -u):$(id -g)"` в `docker run`
  (контейнер идёт от владельца файлов, образу для этого root не нужен: он не пишет ничего вне `/tmp` и каталога задач).
  Организаторы подтвердили, что каталоги задач будут доступны контейнеру на запись.
  На образе с флагами организаторов мы проверили три случая: каталоги у обычного пользователя (uid 1000) с правами по
  умолчанию и `--user 1000:1000` дают 8 ответов из 8; каталоги у произвольного uid 4321 с правами 755/644 и
  `--user 4321:4321` тоже 8 из 8 (включая правку `mylib.py` мутациями); те же каталоги без `--user` дают 0 из 8. При
  старте харнесс печатает в stderr `WARNING: N of M task directories are NOT writable by this process`, а сбой записи не
  считается решением (`write-failed`, итог `answered=0/8` вместо прежнего ложного `6/8`).

## Безопасность

* **Секреты.** Ключ прокси приходит только через переменные окружения запуска и не попадает в образ, файлы, логи и
  отчёты (мы искали его по репозиторию, образу и всем сохранённым логам). Тексты ответов 401 и 403 не сохраняются, потому
  что прокси возвращает в них маску ключа. Логи openJiuwen подняты до `CRITICAL`, иначе на уровне `ERROR` библиотека
  печатала бы промпты целиком и ту же маску.
* **Команды модели.** `bash` запускается в каталоге задачи с минимальным окружением (`PATH`, `HOME=/tmp`, `LANG`), без
  `LLM_API_KEY` и `LLM_BASE_URL`, с таймаутом 30 с на команду и выводом не более 1500 символов. Модель получает только
  поле `instruction`, а `expected` и `check` харнесс не читает. Из сети контейнеру доступен только прокси (так задано
  регламентом), при запуске ничего не скачивается.
* **Пользователь.** Образ работает от root и не задаёт `USER` намеренно. Контейнер запускается с `--cap-drop ALL` и
  `--security-opt no-new-privileges`, то есть без единой capability, а запись `answer.txt` в смонтированный каталог
  задач возможна только владельцу или при открытых правах (см. «Выходные файлы»). Обычный пользователь справился бы с
  этим только при совпадении uid, которого мы не знаем.
* **Файловая система.** Работа совместима с `--read-only`: запись только в каталоги задач и `/tmp`. Логи библиотеки
  отключены от `./logs/`, иначе она не стартует на read-only.
* **Расход.** Есть потолок на задачу, общий бюджет с резервом и клиентская проверка того, что используются только четыре
  разрешённые модели.
* **Известное ограничение.** Агент не изолирован от остальной файловой системы контейнера: команды модели могут читать
  соседние задачи в `/data/tasks`. Других секретов там нет.

## Проверки без токенов

Все наборы одной командой: `tools/run_all_checks.sh <каталог с примерами> [--quick] [--docker]`. Без `--quick` это
несколько минут. Код возврата ненулевой, если упал любой набор, а ключи API перед запуском убираются из окружения, так что
токены не расходуются. По отдельности:

* `tools/check_det.py --seeds 20 --extended --samples <каталог с примерами>`: 920 выполнимых задач из генератора (в том
  числе числа словами и переписанный хвост инструкции) решены верно, неверных ответов и ложных «невыполнимых» нет. Из 400
  невыполнимых распознаны без модели 389, остальные 11 это вопросы про «total cost», которые намеренно уходят к LLM. На
  8 примерах организаторов 8 из 8.
* `tools/check_bug_zoo.py [--no-canon]`: «зоопарк» из 92 вручную написанных вариантов бага в 20 функциях (6 функций пула из
  образцов и их родственники; в каждом файле ещё две исправные функции и тесты в стиле образцов; случай засчитывается,
  только если тесты проходят на исправном коде и падают на баге). Без CANON, когда имя функции неизвестно, мутациями
  чинится 82 из 92 (89%). До добавления обёрток, вызовов методов, замены `=` на `+=`, констант на `len(x)` и `x[0]`,
  сдвига границы среза и `range` без старта было 66 из 92 (72%). Со списком CANON чинится 87 из 92 (95%). Остальные 5 не
  чинятся одной правкой (`return s[0] == s[-1]` вместо сравнения со срезом, `len(s.lower())` вместо подсчёта, пропущенная
  буква в `'aeio'`, `list(set(xs))` вместо порядка, два перепутанных имени в `clamp`) и уходят к LLM.
* `tools/check_repair.py --real <каталог с примерами>`: мутационная починка без знания имён функций (список CANON при
  проверке очищается). 29 вручную написанных случаев с функциями вне CANON (в стиле примеров: перевёрнутое сравнение,
  `-=` вместо `+=`, `s[::1]`, `range` без `+1`, не та переменная, метод класса, три бага в пяти функциях в одном тестовом
  методе) чинятся. 4 случая заведомо не решаются одной правкой (нет подходящей подмены, два бага в одной функции, нет
  ветки для пустого списка, противоречивые тесты), они остаются без результата и уходят к LLM. Ложных `DONE` нет. Оба
  настоящих coding-примера чинятся одними мутациями, без CANON, примерно за 1 с.
* `tools/check_search_chains.py <каталог с примерами>`: на настоящих KB организаторов 30780 вопросов (все люди × глубина
  0–5 × 5 целей × перефразировки × 3 формы записи). Эталон считает сам скрипт собственным обходом графа, без кода
  решателя. Верны все 30780. Бессмысленные формулировки («employer of X born») и висячая ссылка на наставника остаются
  без ответа (идут к LLM). Скрипт проверен подстановкой неверных ответов, он поймал все.
* `tools/check_data_filters.py <каталог с примерами>`: на настоящих `sales.csv` 4100 вопросов (метрика × товар × регион ×
  период). Эталон считает модуль `csv` в самом скрипте. Верны все. Другие формулировки («7 to 8», без `inclusive`, другой
  порядок фильтров, `average`, `orders`) остаются за LLM, отсутствующий столбец даёт «невыполнимо». Эту проверку мы тоже
  проверили подстановкой ошибок.
* `tools/check_math_chains.py`: 4000 случайных историй (старт и 1–10 операций в случайном порядке, числа цифрами и
  словами, с «Then» и без). Эталон это прямая симуляция в самом скрипте, без кода решателя. Верны все 4000. Та же история
  с опустошённым слотом распознана как невыполнимая в 3862 случаях из 3862, где слот можно опустошить. 9 заведомо чужих
  формулировок (несогласованное «tripled … a sister warehouse», «rounded to the nearest», десятичные, скорость без срока,
  «sells», «halved», лишнее предложение) остались у LLM. Режим `--selftest` подставляет заведомо неверные ответы и
  требует, чтобы проверка упала. Формулировки новых операций это наши догадки по двум образцам, так что проверка
  подтверждает согласованность разбора и арифметику, а не покрытие слов организаторов.
* `tools/check_edge_cases.py`: 71 граничный случай, где ошибка стоила бы баллов: функции с состоянием, декораторы и
  условные утверждения, записи в незнакомом формате, упоминания в свободном тексте, «a dozen», хвост с другим файлом или
  с лишним условием.
* `tools/check_startup.py <каталог с примерами>`: 8 сценариев неудобного запуска (недоступный `OUT` или `LOG_DIR`, нет
  ключа, каталог задач только через `TASKS`, позиционные аргументы), в каждом нужно получить 8 из 8.

## Репетиция LLM-пути и один отвергнутый опыт

**Репетиция на реальном прокси** (run12, образ с флагами организаторов, `BUDGET=15000` как предохранитель). 12 задач по 3
на тип с формулировками, которых решатели не знают (мы убедились, что ни одну они не берут). Эталон посчитан отдельно от
харнесса. Результат: 10 из 12 верно, 5429 токенов, 97 с, 42 вызова. По типам: data_analysis 3/3 (149–159 токенов),
coding 3/3 (704–881, все с проверкой тестами), search 2/3 (428–955), math 2/3 (239–288). Две ошибки:
* `search_1009`: модель прошла четыре звена цепочки наставников вместо трёх (ошибка на единицу), ответ 1994 вместо 1990.
  Это типичная слабость LLM на глубоких цепочках, а детерминированный обход графа её исключает. Решатель не взял задачу
  только из-за формулировки («What is the birth year of …»). Поэтому грамматика search расширена перефразировками целей и
  новой целью «название работодателя». Теперь все три поисковые задачи репетиции решаются без токенов и верно (проверено
  на тех же каталогах).
* `math_1008`: наша фраза «A customer returns 35 boxes» двусмысленна, модель вычла 35 вместо прибавления. Это слабость
  теста, а не харнесса: в задачах по образцам (отправка, получение, деление, удвоение) такой фразы нет.

Токены на задачу по типам совпали с прежними оценками (math 270, data 157, search 363, coding 889). Выборка маленькая (12
задач) и годится только для того, чтобы увидеть поведение на формулировках за пределами шаблонов, а не как оценка
точности.

**Опробовано и отвергнуто: вся база знаний в промпте** (run13, `trajectories/run13-inline-kb-experiment-rejected/`, 4743
токена). Мы хотели дать модели небольшую базу целиком в сообщении (36 файлов, около 720 токенов в компактном виде), чтобы
она не искала записи вызовами bash, которые занимают 4–7 шагов и 428–955 токенов. Ожидание было 110–150 токенов на
задачу. На тех же трёх поисковых задачах, что в репетиции, стоимость выросла на 48%, 44% и 38% (в сумме на 42%: 1834 → 2598
токенов), ответы лучше не стали (`search_1009` снова 1994 вместо 1990), а новая задача на четыре звена не уложилась в 7
шагов. Причина в том, что модель без рассуждений использует вызовы bash как цепочку мыслей, по одному звену на вызов, и
игнорирует подсказку, что файлы читать не нужно: перепечатывает записи через heredoc или снова читает `kb/`. При этом
каждый вызов теперь пересылает ещё и базу, а вход считается с коэффициентом 1/10. Выборка малая (5 задач), но направление
одно и то же во всех сопоставимых случаях, и механизм понятен. Код из репозитория удалён. Точные ответы на глубокие
цепочки даёт детерминированный обход графа, а не LLM-путь.

## Что проверено, а что нет

Проверено:
* закреплённые зависимости разрешаются, и для всех есть колёса под CPython 3.12 и linux x86_64 (`uv pip compile
  --no-build`);
* они ставятся в окружение Python 3.12.3 (размер `site-packages` 580 МБ, `torch` и CUDA в зависимости не входят), и
  все нужные модули openJiuwen импортируются вместе (импорт занимает около 7 с);
* харнесс целиком проходит офлайн (`--fake-llm`) в этом окружении, есть юнит-проверки счётчика и проверок выполнимости;
* движок openJiuwen работает против мока прокси (`tools/mock_llm_server.py`) при запуске из каталога только для чтения:
  обычные ответы, два инъектированных 429 (повторены и не списаны), ответ `IMPOSSIBLE` на всё (файлы не создаются),
  неверный ключ (чистая ошибка, расход 0, текста ключа нигде нет), консоль тихая;
* переключение движков: без установленного openJiuwen `auto` предупреждает и работает на цикле, строгий
  `--engine openjiuwen` падает с кодом 1, а поломка внутри фреймворка (подмена `_attempt_async`) приводит к запасному
  циклу с одним предупреждением;
* образ (`tools/smoke_image.sh`, Docker 29.1.3): собирается, `docker images` показывает 1,36 ГБ, внутри только модули
  харнесса и `requirements.txt` (`tools/` и траектории исключены `.dockerignore`), секретов в слоях нет, процесс идёт от
  root, Python 3.12.16, `pip check` чистый. В контейнере с флагами организаторов и без сети 8 примеров дают 8/8 за 0
  токенов (openJiuwen импортируется при `--read-only`), две задачи через настоящий LLM-движок дают 1735 и 158 за 359
  токенов;
* реальные прогоны run1–run13 (см. выше). Нормализация ответа и `grade_run.py` проверены на сохранённых ответах run6;
* детерминированные решатели: все проверки из раздела «Проверки без токенов» и сквозные прогоны в боевой конфигурации
  (run9–run11);
* остановка по `answer.txt`: 10 юнит-случаев защиты `answer_ready` (нет файла, пустой файл, команда с `[exit 1]` или
  таймаутом, падающие и проходящие тесты, `IMPOSSIBLE`). Офлайн на моке и на обоих движках число вызовов у не-coding задач
  ровно вдвое меньше (data 10 против 20, math 10 против 20, search 8 против 16), у coding без изменений, потому что при
  падающих тестах остановки нет. На реальном прокси это run7 и run8.

Ограничения этих проверок. Генератор и решатель мы писали сами и по одним и тем же шаблонам, поэтому синтетические
проверки доказывают согласованность разбора, а не покрытие форматов организаторов. Независимое подтверждение пока только
8 настоящих примеров. Обход графа в search и фильтры в data_analysis проверены на настоящих данных организаторов, но сами
формулировки новых комбинаций (глубина цепочки, регион, один месяц, «the mentor of X») это наши догадки по двум образцам
на тип. Мутационная починка проверена на багах, которые мы написали сами (29 случаев и зоопарк из 92 вариантов), и на
двух настоящих примерах. Баги писались без сверки с таблицей мутаций, но нами же, поэтому это оценка охвата типовых
багов, а не гарантия для багов организаторов. Починка берёт только баг в одну небольшую правку на функцию, два
бага в одной функции или недостающая ветка уходят к LLM. Тесты запускаются в дочернем процессе с лимитами памяти (1 ГБ,
`TEST_MEM_MB`) и процессора: функция с бесконечным циклом и `append` без лимита шла около 12 с, пока процесс не
обрывался (память при этом не измерялась), с лимитом тот же прогон занимает 1–2 с, а перебор мутантов с зацикливанием
в худшем нашем случае укладывается в 6 с. Если формулировки финальных задач чуть иные, решатель вернёт `nomatch`, и задача
уйдёт к LLM, то есть заплатим токенами, а не баллами. Опасны только молчаливо неверный разбор и ложное «невыполнима»,
от них защищают якорные шаблоны, проверки согласованности и граничные тесты.

Не проверено:
* время первой сборки образа с нуля на инфраструктуре организаторов (лимит 1000 с). У нас холодная сборка заняла 192 с при
  канале около 2,7 МБ/с (скачивается около 161 МБ), то есть запас примерно в пять раз. При канале хуже примерно 160 КБ/с
  сборка не уложилась бы. На их стороне проверить это нельзя. Повторная сборка из кеша занимает 7 с;
* run1–run4 шли на системном Python 3.14 (движок на stdlib), образ использует 3.12; run5 уже на 3.12 с закреплёнными
  зависимостями;
* поведение на настоящих 429 и при исчерпании бюджета на прокси организаторов, параллелизм выше 3;
* невыполнимые синтетические задачи движком openJiuwen не гонялись (общая политика проверена на stdlib-движке run3 и
  офлайн на openJiuwen);
* выборка мала: 8 выполнимых примеров, p(успех) пока предположение.
