# Бюджетный харнесс для соревнования openJiuwen

Харнесс получает каталог с задачами и общий токен-бюджет, выбирает, какие задачи решать и в каком порядке,
не тратит токены на заведомо невыполнимые и решает остальные дешёвой моделью с коротким циклом инструментов.

> **Статус (читать первым).** Это рабочая версия, но не окончательная.
> * Задачи решает `ReActAgent` из openJiuwen (`ojw_solver.py`) с нашей политикой и нашим счётчиком токенов. Если
>   openJiuwen не загрузился или упал внутри, харнесс переходит на запасной цикл на стандартной библиотеке
>   (`--engine auto`, по умолчанию; в консоли будет `WARNING`). На 8 примерах оба движка дают 20/20 баллов и
>   одинаковый расход (4562 и 4571 токена), см. «Движок openJiuwen».
> * Перед LLM идёт проход детерминированных решателей (`det_solver.py`, организаторы это разрешили): шаблонные задачи
>   math, data_analysis, search и coding с известными функциями решаются за 0 токенов, невыполнимые «по данным»
>   распознаются без модели. Всё, что не совпало с шаблоном слово в слово, уходит к LLM как раньше (см. «Детерминированные
>   решатели»). На 8 примерах организаторов: 8/8 за 0 токенов; на 40 синтетических: 32/32, весь прогон 3270 токенов.
> * Образ собран и проверен скриптом `tools/smoke_image.sh` (Docker 29.1.3): 1,36 ГБ по `docker images` при лимите
>   4 ГБ; с флагами организаторов (`--read-only`, `--cap-drop ALL`, без сети) 8 примеров решаются за 0 токенов, а две
>   задачи через настоящий LLM-движок внутри контейнера дают верные ответы. **Открытое условие:** каталог задач должен быть
>   доступен на запись пользователю контейнера (root без `CAP_DAC_OVERRIDE`), иначе ни один ответ не сохранится
>   (проверено, см. «Выходные файлы»).
> * Бюджет: организаторы дали ориентир 100K токенов и передают его в переменной `BUDGET`; если её нет, харнесс
>   предполагает 100000. Подробности и другие ответы организаторов: раздел «Ответы организаторов».

## Сборка и запуск

```bash
docker build -t hack:latest .

docker run --rm --name run-$TEAM \
  --network hack-net \
  -e LLM_BASE_URL -e LLM_API_KEY \
  -v "$TASKS:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 8 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python \
  hack:latest /app/run_agent.py --tasks-dir /data/tasks
```

Образ: `python:3.12.16-slim-bookworm`, 159 зависимостей закреплены в `requirements.txt`
(получен из `requirements.in` командой `uv pip compile --python-version 3.12 --python-platform x86_64-unknown-linux-gnu`),
ставятся только из готовых колёс (`pip --only-binary=:all:`), без компиляции. Всё скачивается при сборке, во время
запуска ничего не загружается. Ключей в репозитории и в образе нет.

Сборку и проверку образа в тех же ограничениях, что у организаторов (`--read-only`, `--cap-drop ALL`, без сети),
выполняет `tools/smoke_image.sh` (нужен доступ к Docker): время сборки, размер против лимита 4 ГБ, офлайн-прогон на
примерах, проверка прав на запись в каталог задач и, если заданы `LLM_API_KEY` и `LLM_BASE_URL`, две задачи через
настоящий LLM-движок внутри контейнера.

Без Docker (нужен Python 3.11–3.13 и `pip install -r requirements.txt`):
`LLM_BASE_URL=... LLM_API_KEY=... python run_agent.py --tasks-dir <каталог> --out <файл>`.
Проверка конвейера без сети и без токенов: `--fake-llm` (цикл на stdlib) или локальный мок прокси
`python tools/mock_llm_server.py` (печатает порт; затем `LLM_BASE_URL=http://127.0.0.1:<порт>/v1 LLM_API_KEY=mock`),
который подходит и для движка openJiuwen.

### Переменные окружения и параметры

| Переменная / флаг | По умолчанию | Смысл |
|---|---|---|
| `LLM_BASE_URL`, `LLM_API_KEY` | обязательны | адрес и ключ прокси (OpenAI-совместимый `/chat/completions`); нигде не печатаются |
| `TASKS` / `--tasks-dir` | — | каталог с задачами |
| `OUT` / `--out` | `/tmp/solutions.json` | файл решений **или каталог** (тогда `solutions.json` внутри); см. «Выходные файлы» |
| `BUDGET` / `--budget` | 100000 | общий бюджет в выходных токенах (10 входных = 1 выходной); псевдоним `TOKEN_BUDGET`. Организаторы передают `BUDGET`, например `BUDGET=100000` |
| `PER_TASK_CAP` / `--per-task-cap` | 12000 | жёсткий потолок расхода на одну задачу |
| `MAX_PARALLEL` / `--parallel` | 3 | число потоков; у ключа для разработки лимит 3 параллельных запроса |
| `TIME_LIMIT_S` / `--time-limit` | 3300 | после этого новые задачи не стартуют (жёсткий лимит запуска — 1 час) |
| `ENGINE` / `--engine` | `auto` | `openjiuwen` (ReActAgent, строго: без запасного движка; невозможность импорта останавливает запуск, сбой внутри оставляет задачу без ответа), `loop` (цикл на stdlib, без openJiuwen), `auto` (openJiuwen, при сбое запасной цикл) |
| `TIERS` | `qwen3.6-35b-a3b-noreason,qwen3.8-27b-noreason` | порядок моделей для эскалации |
| `LOG_DIR` / `--log-dir` | `$TMPDIR/ojw_logs` | `calls.jsonl` и траектории `traj/<task>.json` |
| `NO_PRECHECK` / `--no-precheck` | выкл. | отключить проверки выполнимости без LLM (для замеров самого решателя) |
| `AUTO_STOP=0` / `--no-auto-stop` | выкл. | отключить остановку по готовому `answer.txt` (только для сравнения расхода) |
| `DETERMINISTIC=0` / `--no-deterministic` | выкл. | отключить проход детерминированных решателей: все задачи уйдут к LLM (для замеров и отладки) |
| `--resume` | выкл. | пропустить задачи, уже записанные в файл `OUT` |

Аргументы командной строки терпимы к вариантам запуска (окончательная команда организаторов будет опубликована
9 ноября): каталог задач принимается как `--tasks-dir`, `--tasks` или `--tasks_dir`, файл решений как `--out`, `--output`,
`--solutions`, `-o` и другие синонимы; два позиционных аргумента читаются как каталог задач и файл решений; любой
неизвестный аргумент игнорируется с предупреждением в stderr, а не роняет запуск.

## Как это устроено

```
run_agent.py   загрузка задач → план → пул потоков → запись результата после каждой задачи
 tasks.py      чтение task.json (поля expected/check не читаются), признаки задач
 prechecks.py  проверки выполнимости БЕЗ LLM (0 токенов)
 planner.py    оценка p(успех) и стоимости, порядок по reward·p/стоимость
 budget.py     общий счётчик токенов, резервы, потолки
 llm.py        клиент прокси (stdlib), только 4 разрешённые модели, повторы, учёт usage
 solver.py     BaseSolver: политика (IMPOSSIBLE, эскалация, потолки), локальная проверка тестов;
               ToolLoopSolver: запасной движок на stdlib
 det_solver.py детерминированные решатели шаблонных задач (0 токенов), проход до планировщика
 ojw_solver.py OjwSolver: движок на openJiuwen ReActAgent + LedgerModel (учёт токенов, повторы)
 results.py    запись answer.txt и файла OUT после каждой задачи (атомарно)
 tools/        probe_usage.py (замер формата usage), mock_llm_server.py (мок прокси для офлайн-тестов),
               gen_tasks.py (генератор синтетических задач в форматах примеров), grade_run.py (оценка прогона),
               check_det.py (проверка детерминированных решателей без токенов)
```

Агент работает в `workspace/` задачи (инструкции говорят «current directory» и файлы лежат там). Если у задачи нет
`workspace/` (например, math), создаётся пустой временный каталог, чтобы агент не видел `task.json`. Дочерний процесс
`bash` получает минимальное окружение и **не видит `LLM_API_KEY` и `LLM_BASE_URL`**.

**Остановка без финального вызова модели** (`solver.answer_ready`, в обоих движках). Раньше каждая задача заканчивалась
отдельным вызовом, где модель лишь писала `DONE` (вся история уходила на вход ещё раз), а в data_analysis добавлялся
проверочный `cat answer.txt`. Теперь попытка завершается сразу после команды, если одновременно: в каталоге есть
непустой `answer.txt` (устаревший удаляется в начале каждой попытки), последняя команда не завершилась ошибкой
(`[exit N]`) и не истекла по времени, и локальные тесты (если они есть) проходят. Если тест падает, диалог идёт дальше
как раньше, поэтому корректность не меняется. В openJiuwen `LedgerModel.invoke` в этом случае возвращает синтетическое
сообщение `DONE`, ничего не списывая; проверка тестов выносится в поток, чтобы не блокировать общий цикл событий.

## Детерминированные решатели (без LLM)

Организаторы разрешили решать задачи без модели («можно решить все, если получится»). `det_solver.py` запускается
**до** планировщика и стоит 0 токенов. Правило: решатель отвечает, только если **вся инструкция** совпадает с известным
шаблоном слово в слово (якорные регулярные выражения, стандартный суффикс инструкции включён) и данные согласованы;
иначе он возвращает `nomatch`, и задача идёт к LLM как раньше. Отказ стоит токенов, а неверный разбор стоил бы баллов,
поэтому правило такое. Исходов три: `answer` (пишем `answer.txt`), `unsolvable` (шаблон совпал, но данные заведомо не
позволяют ответить: файл не создаётся), `nomatch` (к LLM).

| Тип | Что распознаётся | Проверки данных | Невыполнимой считается |
|---|---|---|---|
| math | склад: старт; «ships X boxes per day for D days»; «receives R deliveries of Q boxes each»; деление на K с округлением вниз; удвоение | первое предложение — старт; любое неизвестное предложение → `nomatch` | предложение с «unknown number of boxes» |
| data_analysis | `sales.csv`: сумма `units` товара за месяцы A–B (можно с регионом); выручка `units * price` товара в регионе | заголовок и число строк совпадают с инструкцией, столбцы числовые | — (прочие вопросы уходят к LLM) |
| search | `kb/`: год рождения; город штаб-квартиры работодателя; год рождения наставника; штаб-квартира работодателя наставника; имя наставника; год основания работодателя | заголовки `# Имя`; неоднозначное имя или недостающее поле → к LLM | человека или компании нет в базе (имя не встречается ни в одном файле того же вида) |
| coding | `mylib.py` + `test_mylib.py`, текст инструкции точно как в примерах | библиотека канонических реализаций (`reverse_words`, `total`, `maximum`, `minimum`, `average`, `first_n`, `last_n`, `count_even`, `count_odd`, `product`): функции подменяются по одной, пока число падающих тестов уменьшается; `DONE` только если прошли **все** тесты, иначе остаётся исходный файл (или улучшенный) и задачу берёт LLM | — (противоречивые тесты ловит `prechecks.py`) |

**Проверка без токенов:** `python tools/check_det.py --seeds 20 --samples <каталог с примерами>`. На 640 выполнимых
задачах из генератора (20 сидов) верно решены все 640, неверных ответов нет, ложных «невыполнимых» нет; распознаны
невыполнимые «неизвестное количество» (40 из 40) и «нет человека или работодателя в базе» (40 из 40); противоречивые
тесты и несуществующий столбец уходят к `prechecks.py` или LLM. На 8 примерах организаторов 8 из 8.

**Честное ограничение.** Генератор писал тот же автор, по тем же шаблонам, что и решатель, поэтому 640 из 640 доказывают
согласованность разбора, а не покрытие форматов организаторов. Независимое подтверждение пока только 8 настоящих
примеров. Если формулировки финальных задач чуть иные, решатель вернёт `nomatch`, и задача уйдёт к LLM (цена: токены, не
баллы); опасен лишь молчаливо неверный разбор, от него защищают якорные шаблоны и проверки согласованности. Библиотека
исправлений для coding знает только перечисленные функции.

## Движок openJiuwen

Задачу решает `ReActAgent` (`ojw_solver.py`): `agent.invoke({"query": инструкция})` с одним инструментом `bash`
(`LocalFunction`), нашим системным промптом (`configure_prompt_template`) и потолком шагов (`max_iterations` — потолок
для типа задачи; одна итерация — один вызов модели). Политику (IMPOSSIBLE, эскалация, потолки) он делит с запасным
движком через `BaseSolver`.

**Почему `ReActAgent`, а не `create_deep_agent`.** `prompt_tokens` первого вызова одной и той же задачи на реальном
прокси (запросы перехвачены локальным моком и переиграны с `max_tokens=1`; файлы в
`trajectories/agent-first-request-payloads/`):

| Вариант | `prompt_tokens` |
|---|---|
| наш цикл на stdlib (системный промпт + `bash`) | 452 |
| `ReActAgent` с пустым системным промптом | 362 |
| **`ReActAgent` с нашим системным промптом (выбран)** | **452** (ровно как цикл: фреймворк ничего не добавляет) |
| `DeepAgent` по умолчанию | 568 |
| `DeepAgent` без рейлов безопасности и аномалий | 434 |

`DeepAgent` дороже по умолчанию, заранее шлёт скрытый запрос с картинкой и держит повторы внутри рейла. `ReActAgent`
отправляет ровно то, что ему задали, и его поведение предсказуемо.

**Неочевидные детали openJiuwen 0.1.19, на которые опирается код:**
* **Повторов нет.** `ModelClientConfig.max_retries` в SDK не передаётся, повторы при сбоях живут только в рейле
  `DeepAgent`. `LedgerModel` сам повторяет 429, 5xx и таймауты (до 5 попыток, учитывает `Retry-After`); запрос,
  который мог дойти до модели (таймаут, обрыв), списывается пессимистичной оценкой входа.
* **Ошибки.** Они приходят как `FrameworkError`, настоящая причина лежит в `__cause__` (исключения openai SDK). Для
  401/403 текст ответа выбрасывается: прокси возвращает в нём маску ключа.
* **`temperature` и `max_tokens` по умолчанию не заданы.** `LedgerModel` ставит их на каждый вызов (`max_tokens`
  ограничен остатком бюджета задачи).
* **Учёт токенов.** `LedgerModel.invoke` читает `usage_metadata` ответа (`input_tokens`, `output_tokens`) и списывает в
  `Ledger`; потоковый `stream` запрещён, чтобы не обойти счётчик.
* **Логи.** По умолчанию библиотека пишет файлы в `./logs/` относительно текущего каталога; при `--read-only` и
  `workdir /app` агент не стартует (`FrameworkError 183001`). До первого импорта openJiuwen `ojw_solver.py` меняет
  `DEFAULT_INNER_LOG_CONFIG`: только консоль, уровень `CRITICAL` (на `ERROR` библиотека печатает целиком промпты и маску
  ключа и логирует каждый наш осознанный повтор).
* **Скрытая проба.** `create_deep_agent` с `enable_read_image_multimodal=None` при старте отправляет отдельный запрос с
  картинкой (`max_tokens=64`).
* **Один цикл событий.** Все задачи идут на одном asyncio-цикле в фоновом потоке: общий HTTP-клиент библиотеки должен
  жить на одном цикле, а пул потоков `run_agent.py` синхронный. Идентификаторы агента уникальны на каждую попытку
  (реестры инструментов и сессий общие на процесс); блокирующий `bash` запускается через `asyncio.to_thread`.
* **Запасной переход.** Любое исключение самого фреймворка (не ошибка модели или авторизации) повторяет попытку запасным
  циклом, в консоль один раз печатается `WARNING`.

**Результат на 8 примерах** (`trajectories/run5-samples-openjiuwen`): 20/20, 4562 токена против 4571 у цикла на stdlib,
шаги совпали по каждой задаче.

## Учёт токенов

Стоимость вызова: `completion_tokens + prompt_tokens / 10` (в «выходных токенах»). Факты о прокси, измеренные
`tools/probe_usage.py` (сырые ответы в `trajectories/proxy-usage-probe.json`):

* `usage.completion_tokens` **уже включает токены рассуждений**: у `qwen3.8-27b` 34 токена при `reasoning_tokens=29`;
  у `qwen3.6-35b-a3b` 227 токенов при ответе в 4 символа и рассуждении в 629 символов (поля `reasoning_tokens` там нет
  вовсе). Поэтому `reasoning_tokens` к стоимости **не прибавляются** (иначе двойной счёт).
* Варианты `-noreason` не рассуждают: 3 токена на тот же вопрос против 34 и 227.
* В стриминге `usage` приходит последним чанком при `stream_options.include_usage`.
* Остаток бюджета узнать нельзя (все пробные эндпоинты отвечают 403), поэтому счётчик свой (`budget.py`).
* Ключ для разработки: 120 запросов (окно не сообщается) и не более 3 параллельных запросов (заголовки `X-Ratelimit-*`).
* Если запрос потерян по сети (мог дойти до модели), на счётчик ставится пессимистичная оценка входа
  (3 символа на токен); если `usage` не вернулся — пессимистичная оценка и входа, и выхода.
* Резервирование: перед стартом задача резервирует ожидаемую стоимость; если свободного бюджета не хватает только
  из-за резервов задач в работе, воркер ждёт, а не отказывается от задачи. Под резерв не отдаётся 10% бюджета.

## Оценка расхода и выбор задач

План: порядок по убыванию `reward · p(успех) / ожидаемые_токены`, задачи с `p < 0.15` не берутся. Ожидаемая стоимость
сейчас — средние по реальным замерам с включённой остановкой по `answer.txt` (32 синтетические выполнимые задачи в
форматах примеров, run8), это грубая оценка, а не модель:

| Тип | Ожидаемая стоимость | p(успех), предположение | Замер: run8 (с остановкой, среднее по n) | Раньше: run6 (без остановки) |
|---|---|---|---|---|
| math | 270 | 0.90 | 270 (n=8) | 353 |
| data_analysis | 160 | 0.85 | 157 (n=8) | 309 |
| search | 400 | 0.90 | 363 (n=6), 501 для проб с наставником (n=2) | 458, 622 |
| coding | 890 | 0.80 | 889 (n=8) | 1033 |
| прочее | 1500 | 0.50 | — | — |

До остановки в решении 64% стоимости приходилось на входные токены (run1), в run6 60%, в run8 54%: каждый шаг заново отправляет системный промпт, схему инструмента

`tasks.features()` (число строк CSV, число и размер файлов, длина инструкции), когда накопится больше траекторий.

## Поиск невыполнимых задач

Три слоя, от самого дешёвого. Примеров невыполнимых задач организаторы не дали, поэтому слои 1–2 написаны под формат
примеров и **консервативны** (лучше пропустить проверку, чем отбросить решаемую задачу); на невыполнимые задачи другой
формы они не сработают.

1. **Планировщик, 0 токенов.** Каждый флаг умножает `p` на 0.1 (ниже порога 0.15 задача пропускается):
   * инструкция упоминает файл или каталог, которого нет в `workspace/` (`missing:...`);
   * `search`: имена из вопроса отсутствуют в `kb/` (`entity-not-in-kb`) или у человека указан работодатель без
     файла компании (`employer-not-in-kb`); флаг ставится, только если **все** названные сущности отсутствуют;
   * `coding`: в тестах одна и та же чистая функция модуля с литеральными аргументами проверяется `assertEqual` с
     двумя разными литералами в разных тестовых методах (`contradictory-tests`). Вызовы без аргументов и методы
     объектов (`stack.pop()`, счётчики) намеренно не рассматриваются: они могут честно возвращать разное.
2. **Системный промпт.** Модели разрешено ответить `IMPOSSIBLE`; тогда ответ не пишется, эскалации нет.
3. **Потолки.** Шаги: math и data_analysis — 5, search — 7, coding — 9 (выполнимые примеры укладывались в 3, 3, 4–5, 7);
   потолок токенов на задачу; на более сильную модель решатель переходит **только если локальный тест упал**, но не
   когда кончились шаги (модель посильнее не найдёт данных, которых нет — проверено, см. run2).

Известные пробелы: модель сама почти не сдаётся и выдумывает ответ, если вопрос про несуществующий столбец CSV
(`data_analysis_9003`, около 1 тыс. токенов); а на противоречивых тестах, которые не поймал слой 1, подгоняет код под
тесты (в run2/run3 — глобальным счётчиком вызовов), так что «тесты прошли» не доказывает, что задача решена.

## Выходные файлы и принятые допущения

* `answer.txt` пишется рядом с `task.json` (так ответили организаторы) и дублируется в `workspace/`, сразу после
  решения. Агент работает в `workspace/` и по инструкции пишет файл туда, харнесс затем записывает тот же
  нормализованный ответ в каталог задачи.
* Файл `OUT` — JSON `{task_id: ответ}`, пишется атомарно (временный файл + переименование) после каждой задачи;
  рядом `*.report.json` с расходом и причиной по каждой задаче.
* Для невыполнимых задач (`IMPOSSIBLE`, пропущенных, без ответа) файл **не создаётся** (требование организаторов); если
  модель успела написать `answer.txt` и затем сдалась, файл удаляется (`ResultStore.clear`).
* Ответ нормализуется: `680.0` → `680` (`solver.normalize_answer`). Модель часто суммирует через `float()` и пишет
  `680.0`; проверка `exact_int` из примеров отвергла бы верное значение. Остальные ответы только обрезаются по краям.
* Регламент называет `OUT` «выходным файлом», но запускает `mkdir -p "$OUT"`; поддержаны оба варианта. В команде запуска
  из регламента в контейнер передаются только `LLM_BASE_URL` и `LLM_API_KEY`, поэтому без явного `-e OUT` файл
  решений окажется в `/tmp` контейнера, и надёжный результат — `answer.txt` в каталогах задач.
* С `--cap-drop ALL` процесс от root не имеет права обходить права доступа. **Проверено на собранном образе:** если
  каталоги задач принадлежат другому пользователю (обычные права 755/644), запись `answer.txt` и правка `mylib.py`
  дают `PermissionError`, ни один ответ не сохраняется; при `chmod -R a+rwX` на каталог задач всё работает. Внутри
  контейнера обойти это нечем, это должна обеспечить среда запуска. Харнесс при старте печатает в stderr
  `WARNING: N of M task directories are NOT writable by this process`, сбой записи не считается решением
  (`write-failed`, итог `answered=0/8` вместо прежнего ложного `6/8`).

## Безопасность

* **Секреты.** Ключ прокси приходит только через переменные окружения запуска и не попадает в образ, файлы, логи и
  отчёты (проверено поиском по репозиторию, образу и всем сохранённым логам). Тексты ответов `401/403` не сохраняются:
  прокси возвращает в них маску ключа. Логи openJiuwen подняты до `CRITICAL`, иначе на уровне `ERROR` библиотека печатала
  бы промпты целиком и ту же маску.
* **Команды модели.** `bash` запускается в каталоге задачи с минимальным окружением (`PATH`, `HOME=/tmp`, `LANG`) без
  `LLM_API_KEY` и `LLM_BASE_URL`, с таймаутом 30 с на команду и выводом не более 1500 символов. Модель получает только
  поле `instruction`; `expected` и `check` харнесс не читает. Из сети контейнеру доступен только прокси (так задано
  регламентом), при запуске ничего не скачивается.
* **Пользователь.** Образ работает от root и не задаёт `USER` намеренно: контейнер запускается с `--cap-drop ALL` и
  `--security-opt no-new-privileges`, то есть без единой capability, а запись `answer.txt` в смонтированный каталог
  задач возможна только владельцу или при открытых правах (см. «Выходные файлы»); обычный пользователь справился бы
  с этим только при совпадении uid, которого мы не знаем.
* **Файловая система.** Работа совместима с `--read-only`: запись только в каталоги задач и `/tmp`; логи библиотеки
  отключены от `./logs/` (иначе она не стартует на read-only).
* **Расход.** Потолок на задачу, общий бюджет с резервом, клиентская проверка того, что используются только четыре
  разрешённые модели.
* **Известное ограничение.** Агент не изолирован от остальной файловой системы контейнера: команды модели могут читать
  соседние задачи в `/data/tasks`; других секретов там нет.

## Что проверено, а что нет

Проверено:
* закреплённые зависимости разрешаются, и для всех есть колёса под CPython 3.12 / linux x86_64 (`uv pip compile --no-build`);
* они ставятся в окружение Python 3.12.3 (размер `site-packages` 580 МБ; `torch` и CUDA в зависимости не входят),
  и все нужные модули openJiuwen импортируются вместе (импорт около 7 с);
* харнесс целиком проходит офлайн (`--fake-llm`) в этом окружении; юнит-проверки счётчика и проверок выполнимости;
* движок openJiuwen против мока прокси (`tools/mock_llm_server.py`), запуск из каталога только для чтения: обычные
  ответы, два инъектированных 429 (повторены и не списаны), ответ `IMPOSSIBLE` на всё (файлы не создаются), неверный
  ключ (чистая ошибка, расход 0, текста ключа нигде нет), консоль тихая;
* переключение движков: без установленного openJiuwen `auto` предупреждает и работает на цикле, строгий
  `--engine openjiuwen` падает с кодом 1; поломка внутри фреймворка (подмена `_attempt_async`) приводит к запасному
  циклу с одним предупреждением;
* **образ** (`tools/smoke_image.sh`, Docker 29.1.3): собирается, `docker images` показывает 1,36 ГБ, внутри только модули
  харнесса и `requirements.txt` (`tools/` и траектории исключены `.dockerignore`), секретов в слоях нет, процесс идёт от
